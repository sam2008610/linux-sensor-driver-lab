# Q&A 討論紀錄

## 和其他文件的分工

| 目錄 | 誰寫 | 內容 |
|---|---|---|
| `docs/lessons/` | Claude | 每個階段開始時寫的教材 |
| `docs/qa/` | Claude（本 skill） | 討論紀錄：問題、使用者的想法、推理過程、結論 |
| `docs/notes/` | 使用者 | 用自己的話重寫；本 skill **不寫入** |

`docs/qa/` 是素材，不是使用者的筆記。不要替使用者寫 `docs/notes/`。

## 什麼時候記

**自動**：一段討論收尾（已經用一兩句話講完結論）後，檢查是否符合下列任一項，符合就記：

- 觀念題，推理過程本身是重點（例：為什麼 IRQ handler 裡不能拿 mutex）
- 使用者原本的理解有誤，討論後修正了——這類最優先，面試最常問到這種地方
- bug 的追查過程：現象 → 看了 oops／lockdep／dmesg 的哪裡 → 原因
- 在專案 kernel 樹裡查證過的 API、Kconfig、檔案位置等事實

**不記**：拼字錯誤、一次性的環境小狀況、純指令語法、`docs/lessons/` 裡已經寫過的內容（除非使用者對它有誤解）。

**手動**：使用者打 `/qa-notes` 或說「記下來」，就記最近一段討論，不必符合上述條件。

**跳過**：使用者說「不用記」。

**時機**：蘇格拉底式提問還在進行、使用者還在推理時**不要記**——會打斷思路，也等於先把答案寫出來。
等結論出來再記。

## 步驟

1. 讀 `docs/qa/README.md` 的索引。有合適的主題檔就加進去；沒有才開新檔
   （檔名英文 kebab-case，例：`irq-context.md`），並在索引加一列。
2. 同一個問題已經記過：更新原條目（補充或更正），不重複新增。
3. 依下方格式寫條目，放在主題檔中相關的位置（沒有明顯位置就放最後）。
4. 引用 API、Kconfig、檔案路徑時，以專案使用的 kernel 原始碼 grep 確認，寫上路徑與版本；
   沒查證的明確標「未查證」。
5. **不 commit**。寫完用一行告訴使用者：記在哪個檔、條目標題。使用者看過後自己 commit。
6. 發現之前的條目寫錯：直接更正，並在條目內加「更正（日期）：…」說明改了什麼。

## 條目格式

```markdown
## <問題，一句話>

- 日期：YYYY-MM-DD ・ 階段：N
- 原本的想法：<使用者一開始怎麼想，包括錯的部分；直接發問就寫「直接問」>

**推理過程**
1. <關鍵提問或觀察> → <使用者的回答／推論>
2. ...

**結論**：<一兩句>

**查證**：`<kernel 樹內路徑>`（kernel vX.Y）；未查證：<…>

**面試可能這樣問**：<一兩個問法>
```

bug 追查的條目，「推理過程」改成：現象 → 看了什麼（貼關鍵的 log 行，不貼整段）→ 原因 → 使用者的修法。

## 寫法

- 記推理，不是逐字稿。每個步驟一行，整個條目通常 10–20 行。
- 保留使用者自己的推導和用詞，包括走錯的路——那正是複習的重點。
- 只記討論中出現過的內容，不在紀錄裡補充新知識；要補的話，另外開一段討論。
- 對話用什麼語言就用什麼語言寫；kernel 名詞保留英文。
